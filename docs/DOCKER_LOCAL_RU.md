# Локальный стек одной Docker-командой

Из корня checkout, при запущенном Docker Engine:

```sh
docker compose up -d --build
```

Команда собирает приложение, поднимает PostgreSQL с pgvector, локальный Ollama и подготавливает обе модели. `.env`, Java, Maven, PostgreSQL и Ollama на хосте не нужны. Приложение открывается на [http://127.0.0.1:8080](http://127.0.0.1:8080), вопросы по статьям — на [/ask](http://127.0.0.1:8080/ask).

Для команды, которая дождётся здоровья сервисов или вернёт ошибку:

```sh
docker compose up -d --build --wait --wait-timeout 1800
```

Первый запуск скачивает образы, зависимости сборки и веса моделей; его длительность зависит от сети и ресурсов VM. Последующие запуски используют сохранённые volumes. Если ожидание завершилось ошибкой, сначала проверьте status/logs: уже запущенные сервисы и данные не нужно удалять ради повторной попытки.

## Подготовка Docker на Mac

На текущем Apple Silicon Mac установлен Colima с Linux ARM64 VM: Virtualization.framework, 6 CPU, 12 GiB RAM и 40 GiB data disk. Можно использовать Docker Desktop вместо Colima; два движка одновременно для проекта не требуются. Docker CLI сам по себе не запускает Linux-контейнеры без работающего engine.

При новой установке через существующий Homebrew:

```sh
brew install colima docker docker-compose docker-buildx docker-credential-helper
```

Проверьте плагины и запустите VM:

```sh
docker compose version
docker buildx version
colima start --arch aarch64 --vm-type vz --cpus 6 --memory 12 --disk 40
docker info
```

Если Homebrew-плагины не найдены, зарегистрируйте их в пользовательском каталоге Docker; команды ниже создают только отсутствующие ссылки и не заменяют существующие:

```sh
mkdir -p ~/.docker/cli-plugins
ln -s "$(brew --prefix docker-compose)/bin/docker-compose" ~/.docker/cli-plugins/docker-compose
ln -s "$(brew --prefix docker-buildx)/bin/docker-buildx" ~/.docker/cli-plugins/docker-buildx
```

При наличии старых ссылок сначала проверьте их назначение; не заменяйте конфигурацию другого рабочего Docker-окружения вслепую. На настроенном Mac старые ссылки Docker Desktop сохранены с суффиксом `.pre-colima`, а Compose и Buildx подключены из Homebrew.

Если после удаления Docker Desktop загрузка образов сообщает об отсутствующем `docker-credential-desktop`, проверьте `credsStore` в `~/.docker/config.json`. Сохраните копию файла и замените устаревшее значение `desktop` на `osxkeychain`, сохранив остальные настройки. Его исполняемый файл предоставляет установленный выше `docker-credential-helper`. На текущем Mac установлен helper **0.9.12**, настройка обновлена, исходный config сохранён в backup. На новом Mac без старой настройки Docker Desktop этот ремонт не требуется.

Для проверки выбранного движка используйте `docker context show` и `docker info`. Если ранее использовался Docker Desktop, Colima при старте активирует свой Docker context; volumes принадлежат конкретному движку и сами между ними не переносятся.

Для автозапуска движка при входе пользователя выполните после первой настройки VM:

```sh
brew services start colima
```

На текущем Mac login-задание Homebrew успешно зарегистрировано. Текущая VM была запущена вручную до регистрации; отдельный foreground-процесс service сейчас не работает, поскольку обнаружил уже запущенную VM. После входа дождитесь успешного `docker info` и используйте обычную Compose-команду. Регистрация автозапуска движка не заменяет проверку готовности приложения.

Проверенные версии на 26 октября 2026: Colima **0.10.3** из Homebrew, Docker CLI **29.9.2**, Docker Engine в VM **29.5.2**, Compose **5.6.1**, Buildx **0.38.1**. Работающий ARM64 engine и его ресурсы подтверждены; фактическое успешное выполнение всей Docker-приёмки фиксируется отдельно ниже.

## Что происходит при старте

1. `runtime-init` создаёт недостающие случайные пароль БД и JWT-секрет атомарной парой и готовит права на data volumes. Уже существующие секреты не заменяются; существующая БД без соответствующих секретов или неполная пара останавливают инициализацию с ошибкой.
2. PostgreSQL и Ollama становятся здоровыми. PostgreSQL содержит расширение `vector`; Ollama работает с отключёнными облачными функциями.
3. `models-init` проверяет и получает `qwen3-embedding:0.6b` и `qwen3:4b`, используя постоянное хранилище моделей. Затем выполняет реальный короткий embedding-запрос с проверкой 1024 конечных чисел и короткий chat-запрос. Наличие имени в списке моделей само по себе не завершает подготовку.
4. Приложение стартует после готовности зависимостей, выполняет Liquibase-миграции, включая `rag`, и становится healthy.

Одноразовые init/model-задания могут отображаться как `Exited (0)` — это успешное завершение работы, а не падение. Для долгоживущих app/PostgreSQL/Ollama ожидается рабочий процесс и успешный healthcheck. Наличие моделей и healthy-состояние не доказывают качество ответа по произвольной статье: реальный RAG проверяется отдельным вопросом с источниками.

Сервисы Compose: `runtime-init`, `postgres`, `ollama`, `models-init`, `app`; браузерный `e2e` включается отдельным профилем. Для диагностики подготовки моделей: `docker compose logs --tail=100 models-init`. У загрузки каждой модели свой предел 1500 секунд, у коротких проверочных вызовов — 120 секунд. Общий `--wait-timeout 1800` может истечь на медленной первой загрузке; это не повод очищать volumes.

Используемые образы: PostgreSQL/pgvector `pgvector/pgvector:0.8.7-pg18-trixie`, Ollama `ollama/ollama:0.40.11`, init-инструменты на `python:3.13-alpine`. Приложение собирается через Maven 3.9.9 с Temurin 21 и запускается в Temurin JRE 21 Jammy от UID 1000. В официальных manifest Maven/JRE подтверждена платформа `linux/arm64/v8`; успешный запуск всего набора образов относится к отдельной Docker-проверке ниже.

На новой базе штатные миграции создают администратора `admin` / `admin123`; измените пароль через управление пользователями. Свои статьи нужно создать и опубликовать. Перенесённая база сохраняет существующие документы и учётные записи; она не является содержимым Docker-образа.

## Ежедневные команды

Запуск или обновление после изменения исходников:

```sh
docker compose up -d --build
```

Состояние, логи и завершение просмотра логов:

```sh
docker compose ps -a
docker compose logs --tail=100
docker compose logs -f app
```

`Ctrl+C` завершает только просмотр логов. Остановка проекта:

```sh
docker compose down
```

Обычный down удаляет контейнеры и сеть проекта, **сохраняя volumes**. Следующий up создаёт контейнеры заново и использует те же данные. Для остановки всей Colima VM после остановки проекта:

```sh
colima stop
```

Для повторного запуска используйте `colima start`. Отдельно отключить login-задание можно командой `brew services stop colima`, а включить — `brew services start colima`. Отключение задания не следует считать подтверждением остановки VM, ранее запущенной вручную: проверяйте `colima status`. Если автозапуск не включён, после перезагрузки потребуется ручной старт. Удаление VM через `colima delete` не является обычной остановкой: вместе с VM можно потерять её Docker-данные.

Если 8080 занят, задайте другой порт:

```sh
APP_PORT=8081 docker compose up -d --build
```

Порт приложения публикуется только на `127.0.0.1`. БД и Ollama доступны контейнерам внутри сети Compose и не имеют host-портов; прямое подключение к нативному PostgreSQL на 55434 не относится к этому Docker-стеку.

## Постоянные данные и сброс

Проект использует четыре named volumes:

| Ключ volume в Compose | Путь в контейнере | Что сохраняется |
| --- | --- | --- |
| `postgres_data` | `/var/lib/postgresql`; PGDATA `/var/lib/postgresql/18/docker` | Пользователи, пространства, документы, версии, права, аудит и векторный индекс |
| `content_data` | `/data/git`, `/data/blobs` | Документный Git-репозиторий с Markdown/историей и файлы вложений |
| `ollama_data` | `/models` | Обе модели Ollama |
| `runtime_secrets` | `/run/kb-secrets/current/` | Файлы `db_password`, `jwt_secret`; не выводите их содержимое в логи или сообщения |

Имена volumes относятся к Compose-проекту. Не меняйте имя проекта (`-p` / `COMPOSE_PROJECT_NAME`) для обычного повторного запуска, если ожидаете увидеть те же данные: другое имя обычно создаёт другой набор volumes. Данные нативного `.local/` не подхватываются автоматически.

Для просмотра проекта и его volumes используйте `docker compose ps -a` и `docker volume ls`. Для осознанного полного сброса **выбранного проекта**:

```sh
docker compose down -v
```

Эта команда удаляет базу, статьи, версии, вложения, модели и секреты проекта. Следующий запуск создаёт пустое окружение и может снова скачать модели. Не используйте её для обычной остановки или устранения непонятной ошибки. Не применяйте глобальную очистку volumes для запуска тестов.

Пароль в secrets volume и пароль существующей PostgreSQL-роли должны совпадать. Удаление только secrets volume не сбрасывает пароль БД и не является восстановлением доступа. Для резервного копирования нужны согласованные PostgreSQL/Git/blob-данные и конфигурация доступа; одного Docker-образа или checkout исходников недостаточно.

По умолчанию БД называется `knowledge_base`, пользователь — `kb_user`. Optional `.env.example` содержит только порт приложения; старые `POSTGRES_PASSWORD`, JWT или SSH-настройки из прежней инструкции не заменяют генерируемые secrets. `POSTGRES_DB`/`POSTGRES_USER` можно задать до создания нового окружения, но их изменение не переименовывает уже существующую базу/роль и не переносит данные.

## Перенос существующих статей с Mac

Миграция всего текущего пользовательского набора — отдельная разовая операция. Сначала останавливаются писатели нативного приложения и сохраняются согласованные dump PostgreSQL, документный Git и blobs, включая последние пользовательские добавления и вложения. Затем этот снимок восстанавливается в предназначенные для этого пустые Docker volumes; совместимые модели копируются с проверкой digest. Нативный исходник и backup сохраняются для отката. Исторический демо-набор из 15 статей не должен заменять более свежие данные.

Перед восстановлением целевой проект должен иметь только подготовленные `runtime-init`/PostgreSQL, без работающего app или Ollama. После получения образа Ollama создайте его контейнер без запуска, чтобы Compose создал и пометил model volume правильным именем проекта:

```sh
docker compose --project-name trpo up --no-start --no-deps ollama
```

Это подготовка отдельной миграции в проект `trpo`, а не дополнительный шаг обычного первого запуска. Нельзя подменять её произвольным `docker volume create`: миграция проверяет принадлежность всех четырёх volumes выбранному Compose-проекту и отказывается от непустых целевых БД/контента.

Перед переключением проверяются идентификаторы документов, строки версий, ссылки `Git SHA:path`, вложения, чтение/история/экспорт и реальный ответ RAG. После down/up проверки повторяются. Обычная Compose-команда не импортирует демо поверх новых пользовательских правок.

При выполненном переносе снимок `.local/backups/docker-2026-10-26-213642` содержал **17 документов, 15 версий, 1 вложение, 2 пространства и 1 пользователя**. Это полный актуальный набор: пользователь успел добавить два документа и вложение после прежнего демо. Восстановление подтвердило точные fingerprints всех таблиц, hashes контента/моделей, 15 ссылок `Git SHA:path` и ссылку на вложение; отчёт — `restore-20261026-213730.json` в каталоге backup.

После переноса пользователь опубликовал документ №17, и число версий стало **16**. Перед проверкой down/up был снят новый согласованный baseline с этой публикацией. Сравнение с прежним снимком закономерно отличалось; публикацию не откатывали. Проверять сохранность при рестарте нужно относительно последнего согласованного состояния, а не восстанавливать старые значения ради совпадения fingerprint.

[Нативный стек](LOCAL_SETUP_RU.md) остаётся альтернативой; он хранит свои данные отдельно и слушает приложение на 18081. Если после миграции редактировать обе копии, они станут независимыми наборами данных: автоматической синхронизации между native и Docker нет.

## Локальный AI и ресурсы

В Docker-профиле `AI_ENABLED=false`, `NOTIFICATIONS_ENABLED=false`, `OLLAMA_NO_CLOUD=1`. RAG использует внутренний сервис Ollama с `qwen3-embedding:0.6b` (1024 измерения) и `qwen3:4b`. Предельное время отдельного вызова модели настроено на 120 секунд; превышение даёт контролируемую ошибку, а не обещание ответа за это время.

В выбранной Linux VM на Mac модель работает на **CPU**, без доступа к нативному Metal. Сохранённые ранее замеры нативного RAG нельзя переносить на Docker. Для более быстрой локальной генерации на этом Mac доступен нативный workflow; его настройка не требуется для работы Compose.

Публикации индексируются асинхронно. Healthy приложение может ещё обрабатывать новые статьи; отсутствие ответа по свежему документу требует проверки очереди, статуса публикации и прав пользователя. [Подробные RAG-контракты, очереди и ограничения](RAG_LOCAL.md).

## Диагностика и проверки

| Симптом | Проверка |
| --- | --- |
| `Cannot connect to Docker daemon` | Запущен ли Colima/Docker Desktop, какой `docker context show`, работает ли `docker info` |
| `compose` или `buildx` не найден | Версии и ссылки plugins из раздела подготовки |
| Не удалось скачать VM, image или model | Сеть и журнал ответственного сервиса; повторный запуск сохраняет уже подготовленные данные |
| Init/model job завершился не с кодом 0 | `docker compose ps -a` и `docker compose logs --tail=100` |
| Занят 8080 | Другой `APP_PORT`; не завершайте произвольный чужой процесс |
| App unhealthy | Логи `app`, затем PostgreSQL/model init; не стирайте volumes как первый шаг |
| Статьи «пропали» | Проверить Docker context и имя Compose-проекта; другой engine/project использует другие volumes |
| RAG долго отвечает | Логи Ollama, CPU/RAM VM, загрузка модели и очередь; CPU VM отличается от Metal |

Полные regression-команды описаны в [quality gates](../openspec/quality-gates.md). Автоматические тесты запускаются отдельным Compose-проектом с собственными volumes, без изменения пользовательских данных. Проверка контейнеров и smoke не заменяют исходную оценку качества RAG по 40 вопросам.

Сценарий браузерных тестов требует Python 3 на хосте в дополнение к Docker/Compose:

```sh
./run-e2e.sh
# Либо отдельный набор:
./run-e2e.sh npx playwright test --grep @strict
```

Runner создаёт случайное имя тестового проекта, игнорирует пользовательский `.env`/project/profile selection, проверяет отсутствие общих mounts/портов и удаляет только собственные test volumes при завершении. В этом браузерном окружении `RAG_ENABLED=false`: явный тестовый override пропускает подготовку моделей и исключает Ollama из зависимостей app и models-init. Поэтому `./run-e2e.sh` не скачивает образ Ollama и не запускает его сервер. Guard проверяет и транзитивные зависимости до запуска контейнеров; граф backend состоит из app, runtime-init, postgres и models-init. Это не меняет обычный Compose-стек с включённым RAG. Браузерные проверки RAG UI используют подставленные ответы и не подтверждают настоящую модель. Отчёты копируются в `.local/e2e-results/<project>/` перед очисткой.

Сокращения Make: `make dev-up`/`make run` — build/up с ожиданием здоровья, `make status`, `make dev-logs`, `make dev-down`; `make build` только собирает image приложения, `make docker-shell` открывает диагностический `sh` в работающем app, `make e2e` запускает изолированный runner. Исходников и Maven в runtime-контейнере нет; редактируйте checkout на хосте.

[Скрипты разработки](../scripts/dev/README.md) открывают host checkout в редакторе. Для разработки внутри VS Code доступен отдельный [Dev Container](../.devcontainer/README.md) с Maven/JDK 21 и подключённым checkout. Он не является runtime-контейнером приложения и не подключает Docker socket или SSH-ключи. PowerShell-обёртки и конфигурация VS Code проверены статически; интерактивный запуск этих вариантов на данном Mac не выполнялся.
