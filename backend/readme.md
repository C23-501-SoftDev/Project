#### Создание базы данных (через pgAdmin)

1. Откройте pgAdmin
2. Подключитесь к серверу
3. В окне Query Tools (Инструмент запросов) для базы postgres введите следующий SQL-запрос(создание пользователя для работы с БД):

```sql
CREATE USER kb_user WITH PASSWORD 'strong_password';
```

А затем этот (создание самой БД):

```sql
CREATE DATABASE knowledge_base
   WITH 
   OWNER = kb_user
   ENCODING = 'UTF8'
   CONNECTION LIMIT = -1;
```

## Локальная разработка в Docker (для команды)

### Запуск из корня репозитория

Требуется работающий Docker Engine с Compose. Java/Maven на хосте, `.env`, SSH-ключи и Git-конфигурация для запуска не нужны:

```bash
docker compose up -d --build
```

Для явного ожидания готовности используйте `docker compose up -d --build --wait --wait-timeout 1800` или `make dev-up`. Приложение доступно на <http://127.0.0.1:8080>. Первое скачивание образов и моделей может занять значительное время; подробности, ограничения и актуальные результаты проверки — в [Docker-инструкции](../docs/DOCKER_LOCAL_RU.md). Постоянный native-запуск на macOS описан [отдельно](../docs/LOCAL_SETUP_RU.md).

### Образы, данные и зависимости

`backend/Dockerfile` собирает JAR в Maven/JDK 21 и запускает его в отдельном JRE 21 от UID 1000. Исходники остаются в checkout на хосте; в работающий контейнер они не монтируются, автоматической пересборки при сохранении файла нет. Maven в runtime-образе не установлен. Зависимости скачиваются на этапе сборки образа, Liquibase применяет миграции при старте приложения.

Compose содержит сервисы `runtime-init`, `postgres`, `ollama`, `models-init`, `app` и дополнительный профиль `e2e`. PostgreSQL 18 с pgvector и Ollama доступны только внутри Compose; наружу публикуется приложение на loopback. `models-init` получает отсутствующие модели и проверяет embedding/короткую генерацию до запуска приложения. Внешние AI и SMTP выключены.

Именованные тома `postgres_data`, `content_data`, `ollama_data`, `runtime_secrets` сохраняют БД, Git/вложения, модели и случайно сгенерированные секреты. Повторный запуск их не заменяет. Старые `POSTGRES_PASSWORD`/`JWT_SECRET_KEY` из `.env` не используются: приложение читает сгенерированные файлы. `APP_PORT` — необязательное переопределение порта, например `APP_PORT=8081 docker compose up -d --build`.

### Повседневные команды

Выполняйте из корня checkout и используйте один и тот же Compose-проект; для явно выбранного проекта передавайте одинаковый `-p <имя>` во всех командах.

| Команда | Что делает |
|---------|-----------|
| `make dev-up` | Собирает и запускает стек с ожиданием готовности |
| `docker compose ps -a` | Показывает сервисы, включая завершившиеся init-задачи |
| `docker compose logs --tail=100 app postgres models-init` | Показывает диагностику приложения, БД и моделей |
| `make dev-logs` | Следит за логами стека |
| `make docker-shell` | Открывает диагностический shell сервиса `app` |
| `docker compose down` | Останавливает выбранный проект, сохраняя четыре тома |
| `./run-e2e.sh` | Запускает браузерные тесты в отдельном временном Compose-проекте |

Backend-тесты запускайте из `backend` командой `mvn clean verify` при установленном JDK/Maven, а не через shell runtime-контейнера. Полный набор проверок — в [quality-gates](../openspec/quality-gates.md).

### Если запуск не завершился

Проверьте `docker compose ps -a` и логи соответствующего сервиса: `runtime-init` отвечает за целостность секретов и права томов, `postgres` — за БД, `models-init` — за загрузку и доступность локальных моделей. Ошибка или таймаут ожидания не подтверждает готовность приложения. При занятом порте задайте другой `APP_PORT`.

Если секреты потеряны при существующей БД, восстановите согласованный набор томов/резервную копию по [Docker-инструкции](../docs/DOCKER_LOCAL_RU.md); обычная инициализация откажется менять пароль существующей БД. Не удаляйте тома для устранения обычной ошибки запуска. Намеренный `docker compose down -v` удаляет все четыре тома выбранного проекта вместе с документами, историей, вложениями, моделями и секретами; это отдельный разрушительный сброс, не часть повседневного workflow.

## 📖 Где работать после успешного запуска

После того как контейнеры запущены и приложение доступно по <http://localhost:8080>, вот рекомендуемый workflow:

### 1. Проверить, что всё работает

- Откройте <http://localhost:8080> в браузере
- Смотрите страницу входа (или главную, если уже авторизованы)
- Откройте <http://localhost:8080/actuator/health> — должна быть `"status":"UP"`

### 2. Понять структуру кода

```
backend/src/main/java/com/knowledgebase/
├── application/        # Spring компоненты, конфигурация, сервисы
├── domain/            # Бизнес-логика, ентитеты, интерфейсы репозиториев

```

### 3. Начать разработку

1. **Выбрать слой для изменений:**
   - API? → `interfaces/` (контроллеры)
   - Бизнес-логика? → `application/` (сервисы)
   - Новая сущность? → `domain/` (entity, repository interface)
   - Запросы в БД? → `infrastructure/` (repository impl)

2. **Редактировать файл:**
   - Откройте файл в VS Code
   - Сохраните (Cmd+S / Ctrl+S)
   - Смотрите логи: `make dev-logs`

3. **Пересоберите образ после изменения кода:**
   - Из корня выполните `docker compose up -d --build --wait --wait-timeout 1800`.
   - Дождитесь успешной готовности сервисов; сохранение файла само по себе не обновляет контейнер.

4. **Тестируйте:**
   - Обновите браузер (F5 / Cmd+R)
   - Используйте Swagger UI: <http://localhost:8080/swagger-ui.html>
   - Или проверьте логи для ошибок

## 🔌 REST API

Все API-эндпоинты описаны через OpenAPI (Swagger UI). Это основной способ изучения доступных методов, параметров и форматов ответов. **Для тестирования эндпоинтов рекомендуется использовать Swagger UI**, а не curl/Postman.

Swagger UI: **<http://localhost:8080/swagger-ui.html>**
Swagger UI: **<http://localhost:8080/swagger-ui.html>**

### Аутентификация через Swagger

1. Откройте Swagger UI
2. Сначала откройте `/login` в том же браузере: сервер выдаст Cookie `XSRF-TOKEN`. Затем найдите раздел **Authentication** → `POST /api/auth/login`; Swagger UI передаст токен через `X-XSRF-TOKEN`.
3. Нажмите **Try it out**, введите учётные данные:

   ```json
   { "login": "admin", "password": "admin123" }
   ```

4. Сервер установит HttpOnly Cookie `JWT`; браузер отправляет её автоматически в том же origin.
5. Для POST/PUT/PATCH/DELETE Swagger UI также отправляет `X-XSRF-TOKEN`. При 403 проверьте наличие Cookie и заголовка, а также права пользователя.
6. При обращении из собственного API-клиента сохраняйте обе Cookie и передавайте CSRF-заголовок, включая запрос входа. Один заголовок Bearer не заменяет Cookie-аутентификацию этого приложения.

### Аутентификация

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/auth/login` | Вход по логину/паролю (JSON). Возвращает JWT-токен и устанавливает HttpOnly Cookie |
| GET | `/api/auth/me` | Информация о текущем пользователе |

**Пример ответа `/api/auth/login`** (200 OK):

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "user": {
    "id": 1,
    "login": "admin",
    "email": "admin@knowledgebase.local",
    "role": "ADMIN"
  }
}
```

### Управление пользователями (только ADMIN)

**Базовый путь:** `/api/admin/users`

| Метод | Путь | Описание | Параметры |
|-------|------|----------|-----------|
| GET | `/api/admin/users` | Список пользователей с пагинацией | `page` (0-based), `size`, `sortBy`, `sortDir` |
| GET | `/api/admin/users/{id}` | Данные конкретного пользователя | |
| POST | `/api/admin/users` | Создание пользователя | Тело: `{ login, email, password, role }` |
| PUT | `/api/admin/users/{id}` | Обновление логина/email/роли | Тело: `{ login, email, role }` |

## 🔐 Роли и права

| Роль | Описание |
|------|----------|
| **ADMIN** | Полный доступ. Управление пользователями, пространствами и правами. Видит все пространства. |
| **EDITOR** | Создание и редактирование документов в пространствах с правом `WRITE`. |
| **READER** | Только чтение в пространствах с правом `READ`. |

ADMIN автоматически получает `[READ, WRITE, OWNER]` во всех пространствах.

## 🛡️ Безопасность

- **JWT в HttpOnly Cookie** — токен недоступен из JavaScript
- **CSRF защита** — Cookie-based токен для AJAX-запросов
- **BCrypt** — хеширование паролей (strength 10)
- Двойная проверка ролей: на уровне SecurityConfig + `@PreAuthorize` на методах контроллеров
