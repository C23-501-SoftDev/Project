# E2E-тестирование через интерфейс (без командной строки)

> Инструкция «потыкать руками» для приёмки шести фич. Всё проверяется мышкой:
> где есть страница в админ-панели — тыкаем там; где страницы нет (группы, аудит,
> тест SMTP) — тыкаем в **Swagger UI** (визуальная форма для API прямо в браузере).
> Журнал действий смотрим **в таблице логов**, а не на сайте — как именно, см. раздел 8.
>
> Проверено вживую 2026-07-21: авторизация в системе идёт через cookie, поэтому после
> входа на сайт и Swagger UI, и переход по API-ссылке в адресной строке работают
> автоматически — токен подставлять никуда не нужно.

---

## 0. Что нужно до начала

1. Поднять окружение (один раз):
   - **Docker Desktop** запущен.
   - В папке проекта: `docker compose --env-file .env up -d --build` (или `make dev-up`).
   - Подождать, пока `kb_app` в Docker Desktop станет **healthy** (~1–2 мин).
2. Открыть браузер: **http://localhost:8080** → страница входа.
3. Войти: логин **admin**, пароль **admin123** → попадаем на главную.

> После входа браузер держит сессию. Все ссылки вида `http://localhost:8080/...`
> в этой же вкладке уже авторизованы.

### Где что тестируется (карта)

| US | Фича | Где тестировать в браузере |
|----|------|----------------------------|
| US4.2.1 | CRUD пространств | **UI**: Админ-панель → «Пространства» |
| US4.2.2 (личные права) | Права пользователю на пространство | **UI**: «Пространства» → кнопка «Права» |
| US4.2.2 (права групп) | Права группе на пространство | **Swagger UI** (страницы нет) |
| US4.1.8 | CRUD групп | **Swagger UI** (страницы нет) |
| US4.1.9 | Членство в группах | **Swagger UI** (страницы нет) |
| US4.1.5 | Журнал аудита | **Таблица логов** `audit_log` (см. раздел 8) |
| US4.3.1 | Email-уведомления | **Swagger UI** (`/notifications/test`) + логи |

> Вспомогательно нам понадобятся тестовые пользователи с ролью **GUEST** — их создаём
> в UI на странице «Пользователи» (раздел 1). GUEST — единственная роль, доступ которой
> к пространству определяется только выданными правами, поэтому на ней удобно проверять
> и личные права (US4.2.2), и права через группу.

### Как открыть Swagger UI

- Со страницы входа есть ссылка **«Swagger UI»**, либо прямой адрес:
  **http://localhost:8080/swagger-ui/index.html**
- Разделы, которые нам нужны: **Groups**, **Spaces**, **Audit**, **Notifications**.
- Порядок действий в Swagger одинаковый: раскрыть эндпоинт → **Try it out** →
  заполнить поля/тело → **Execute** → смотреть блок **Server response** (код + тело).
- Кнопку **Authorize** (замочек) трогать **не нужно** — авторизация идёт через
  cookie, полученный при входе на сайт в той же вкладке браузера.

## 1. Тестовые пользователи (подготовка, UI)

**Страница:** Админ-панель (кнопка сверху справа) → вкладка **«Пользователи»** (`/admin/users`).

1. Нажать **«+ Создать пользователя»**.
2. Заполнить: Логин `guest1`, Email `guest1@example.com`, Роль — **Гость**, галочку
   «Администратор» не ставить, Пароль `guest123`. Нажать **Сохранить**.
3. Повторить и создать `guest2` / `guest2@example.com` / роль **Гость** / пароль `guest123`
   (пригодится для проверки групп).
4. Убедиться, что пользователи появились в таблице с ролью **Гость** и статусом **Активен**.

**Проверка soft-delete/restore (заодно):** у строки `guest2` нажать **Удалить** →
подтвердить → в фильтре «Статус» выбрать **Удалённые** → строка видна как «Удалён» →
нажать **Восстановить** → вернуть фильтр на **Активные**.

## 2. US4.2.1 — CRUD пространств (UI)

**Страница:** Админ-панель → **«Пространства»** (`/admin/spaces`).

### Сценарий 1 — Создание

1. **«+ Создать пространство»** → Название `Demo`, Описание `демо-пространство`,
   Владелец — выбрать себя (**admin**). Сохранить.
2. В списке появилась строка `Demo`, владелец `admin`, статус **Активен**.

> В выпадающем списке «Владелец» показываются **только администраторы** — это и есть
> бизнес-правило US4.2.1 «владельцем может быть только админ», встроенное в интерфейс.

### Сценарий 2 — Уникальность имени

3. Снова «+ Создать пространство» с тем же именем `Demo` → появится **ошибка** (тост
   «Ошибка сохранения»), второе пространство не создаётся (сервер отвечает `409 Conflict`).

### Сценарий 3 — Редактирование

4. У строки `Demo` нажать **Редактировать** → изменить Описание на `обновлено` → Сохранить.
5. Описание в таблице обновилось.

### Сценарий 4 — Soft-delete и восстановление

6. У строки `Demo` нажать **Удалить**. Строка исчезает из списка активных.
7. В фильтре «Статус» выбрать **Удалённые** → нажать **Применить** → `Demo` виден со
   статусом **Удалён**, доступна кнопка **Восстановить**.
8. Нажать **Восстановить** → подтвердить → вернуть фильтр на **Активные** → `Demo` снова активен.

> Пункт про «владельца только админ» через интерфейс не обойти (в списке нет не-админов).
> Если нужно увидеть саму ошибку `422` — это делается в Swagger (`PUT /api/admin/spaces/{id}`
> с `ownerId` не-админа), но для приёмки достаточно того, что UI не даёт выбрать не-админа.

## 3. US4.2.2 (личные права) — права пользователю на пространство (UI)

**Страница:** Админ-панель → **«Пространства»**. Понадобится активное пространство `Demo`
(из раздела 2) и пользователь `guest1` (из раздела 1).

### Выдача права

1. У строки `Demo` нажать **«Права»** — откроется окно «Управление правами доступа».
2. В списке «Пользователь» выбрать `guest1`, «Тип доступа» — **Read**, нажать **Добавить право**.
3. Внизу в «Текущие права доступа» появилась строка `guest1 — READ` с кнопкой **Отозвать**.

### Проверка, что доступ реально появился

4. Открыть **второе окно браузера в режиме инкогнито** → http://localhost:8080 →
   войти как `guest1` / `guest123`.
5. На главной у `guest1` в списке пространств виден **Demo** (до выдачи права его не было).

### Повышение до Write и отзыв

6. Вернуться в окно admin → снова «Права» у `Demo` → выбрать `guest1`, тип **Write** →
   **Добавить право**. Теперь у guest1 есть доступ на редактирование.
7. Нажать **Отозвать** напротив права `guest1` → право пропало.
8. В окне инкогнито обновить главную у `guest1` → пространство `Demo` больше **не отображается**.

> Соответствие критериям приёмки US4.2.2: сценарий 1 (READ → guest видит пространство),
> сценарий 2 (WRITE → может редактировать), сценарий 4 (отзыв → доступ пропадает).

## 4. US4.1.8 — CRUD групп (Swagger UI)

Страницы для групп нет — тестируем в **Swagger UI**, раздел **Groups**.
(http://localhost:8080/swagger-ui/index.html)

### Сценарий 1 — Создание группы

1. `POST /api/admin/groups` → **Try it out** → тело:
   ```json
   { "name": "Аналитики", "description": "группа для теста" }
   ```
   **Execute** → ответ **201**, в теле есть `id` (запомнить его, дальше `<groupId>`),
   `memberCount: 0`.
2. Повторить **Execute** с тем же `name` → ответ **409** (имя уникально).

### Просмотр и обновление

3. `GET /api/admin/groups` → **Execute** → в `content` видна созданная группа.
4. `PUT /api/admin/groups/{groupId}` → подставить `<groupId>`, тело
   `{ "name": "Аналитики 2.0", "description": "переименовано" }` → **201/200**, имя изменилось.

### Сценарий 2 — Удаление

5. `DELETE /api/admin/groups/{groupId}` → **204**.
6. `GET /api/admin/groups/{groupId}` → **404** (группы больше нет).

> Важное свойство (US4.1.8, сценарий 2): при удалении группы автоматически снимаются
> все её членства и все права группы на пространства. Это проверим сквозным сценарием в разделе 6.

## 5. US4.1.9 — членство в группах (Swagger UI)

Раздел **Groups**. Заранее создать группу (раздел 4, шаг 1) — пусть её id будет `<groupId>`.
Понадобятся id пользователей `guest1`/`guest2`: взять из `GET /api/admin/users`
(поле `id`) или из таблицы на странице «Пользователи».

### Сценарий 1 — Добавление в группу

1. `POST /api/admin/groups/{groupId}/members` → тело `{ "userId": <id guest1> }` → **201**.
2. Повторить с тем же `userId` → **409** (уже в группе).
3. `GET /api/admin/groups/{groupId}/members` → **200**, в списке `guest1` (login, email).
4. `GET /api/admin/groups/{groupId}` → `memberCount` увеличился.

### Сценарий 2 — Удаление из группы

5. `DELETE /api/admin/groups/{groupId}/members/{userId}` → **204**.
6. Повторить тот же DELETE → **409** (уже не состоит).
7. `GET .../members` → список без этого пользователя.

## 6. US4.2.2 (права групп) — сквозной сценарий «доступ через группу» (Swagger UI + UI)

Самый показательный тест: участник группы наследует права группы на пространство.

Подготовка: активное пространство `Demo` (раздел 2), пользователь `guest1` (раздел 1),
группа (раздел 4). Нужны их id.

1. **Swagger → Groups:** `POST /api/admin/groups/{groupId}/members`,
   тело `{ "userId": <id guest1> }` → **201** (guest1 в группе).
2. **Swagger → Spaces:** `POST /api/admin/spaces/{spaceId}/group-permissions`,
   тело `{ "groupId": <groupId>, "permissionType": "READ" }` → **201**.
3. **Проверка доступа:** в окне инкогнито войти как `guest1` → на главной виден `Demo`
   (доступ пришёл **через группу**, личных прав ему не выдавали).
4. **Список прав групп:** `GET /api/admin/spaces/{spaceId}/group-permissions` → видно право `READ`
   с названием группы.
5. **Отзыв доступа тремя способами** (любой на выбор, каждый убирает доступ у guest1 —
   проверять обновлением главной в окне инкогнито):
   - `DELETE /api/admin/group-permissions/{permId}` — отозвать право группы;
   - `DELETE /api/admin/groups/{groupId}/members/{userId}` — убрать guest1 из группы (US4.1.9);
   - `DELETE /api/admin/groups/{groupId}` — удалить группу целиком (US4.1.8): право группы
     тоже исчезнет — проверить `GET .../group-permissions` (пусто).

> Так закрываются сценарии US4.2.2 для групп + связка с US4.1.8/US4.1.9.

## 7. US4.3.1 — Email-уведомления (Swagger UI + логи)

Страницы «Настройки» пока заглушка, поэтому проверяем через **Swagger UI**, раздел **Notifications**.
По умолчанию `NOTIFICATIONS_ENABLED=false` — реальный SMTP не нужен, факт отправки пишется в лог.

### Тестовое письмо (проверка конфигурации)

1. `POST /api/admin/notifications/test` → **Try it out** → тело `{ "recipient": "you@example.com" }`
   → **Execute** → ответ **202** и тело `{ "recipient": "you@example.com", "queued": true,
   "notificationsEnabled": false }`.
2. Без поля recipient (тело `{}`) → письмо уходит на адрес администратора по умолчанию,
   ответ **202**.

### Событийные письма

3. Уведомления генерируются автоматически при действиях (всё это делается в UI/Swagger,
   которые уже проверялись выше):
   - создание пользователя (раздел 1) → приветственное письмо;
   - выдача права на пространство (раздел 3) → письмо о правах;
   - изменение документа → письма участникам пространства.
4. Факт отправки при `NOTIFICATIONS_ENABLED=false` виден в **логах приложения** контейнера
   `kb_app` (Docker Desktop → контейнер `kb_app` → вкладка **Logs**, поиск по слову `email`).

> Реальная отправка: в `.env` выставить `NOTIFICATIONS_ENABLED=true` и `MAIL_HOST/PORT/USERNAME/PASSWORD`,
> перезапустить контейнер, повторить шаг 1 — письмо придёт на ящик.

## 8. US4.1.5 — журнал аудита: смотрим в ТАБЛИЦЕ логов (не на сайте)

Журнал действий пишется в таблицу БД **`audit_log`**. Правильный способ смотреть его —
именно в таблице, а не через страницу/эндпоинт. Ниже — как это сделать быстрее всего.

### Параметры подключения к базе (одни на все способы)

| Параметр | Значение |
|----------|----------|
| Host | `localhost` |
| Port | `5433` |
| База (Database) | `knowledge_base` |
| Пользователь | `kb_user` |
| Пароль | `strong_password` |
| Таблица | `audit_log` |

### Способ A (самый быстрый, без установки) — таблица в Docker Desktop

1. Docker Desktop → контейнер **`kb_postgres`** → вкладка **Exec** (терминал контейнера).
2. Вставить одну строку и Enter:
   ```
   psql -U kb_user -d knowledge_base -c "SELECT created_at, user_login, action_type, resource_type, resource_id, details FROM audit_log ORDER BY created_at DESC LIMIT 20;"
   ```
3. Появится таблица последних 20 действий: кто (`user_login`), что (`action_type`),
   над чем (`resource_type`/`resource_id`), детали и время.

### Способ B (визуальный, кликом) — GUI-клиент БД

Подойдёт **DBeaver**, **pgAdmin**, или встроенная панель **Database** в IntelliJ IDEA / DataGrip
(если проект уже открыт в IDE — это самый быстрый путь, без установки нового ПО):

1. Создать новое подключение **PostgreSQL** с параметрами из таблицы выше.
2. В дереве раскрыть базу → **Tables** → **`audit_log`** → двойной клик.
3. Открывается таблица-гридом: сортировка по колонке `created_at` (клик по заголовку),
   фильтры по колонкам прямо в шапке — SQL писать не нужно.

### Что проверять (критерии приёмки US4.1.5)

Сначала выполнить любые действия из разделов 1–7 (создать пространство, выдать право,
создать/удалить группу, изменить документ), затем открыть таблицу:

- **Сценарий 1** — операции над документами дают строки `DOCUMENT_CREATED/UPDATED/DELETED`;
- **Сценарий 2** — админ-операции журналируются с деталями, например смена роли:
  `USER_UPDATED` в колонке `details` содержит старое и новое значение (`GUEST -> READER`),
  а выдача прав — `PERMISSION_GRANTED` с пространством/пользователем/типом;
- у каждой строки заполнены `user_login`, `created_at` и `ip_address`.

### Фильтры прямо в SQL (Способ A) — под сценарий 4 приёмки

```sql
-- по конкретному пользователю
SELECT * FROM audit_log WHERE user_id = 1 ORDER BY created_at DESC;

-- по типу действия
SELECT * FROM audit_log WHERE action_type = 'SPACE_CREATED' ORDER BY created_at DESC;

-- по диапазону дат
SELECT * FROM audit_log
WHERE created_at >= '2026-07-21 00:00:00'
ORDER BY created_at DESC;
```

Основные значения `action_type`: `DOCUMENT_CREATED/UPDATED/DELETED/HARD_DELETED/RESTORED`,
`SPACE_CREATED/UPDATED/DELETED/HARD_DELETED/RESTORED`,
`USER_CREATED/UPDATED/DELETED/RESTORED/PASSWORD_CHANGED`,
`PERMISSION_GRANTED/REVOKED`, `GROUP_PERMISSION_GRANTED/REVOKED`,
`GROUP_CREATED/UPDATED/DELETED`, `GROUP_MEMBER_ADDED/REMOVED`.

### Проверка ограничения доступа (сценарий 3)

Эндпоинт журнала закрыт для не-админов. Быстро убедиться: в окне инкогнито войти как
`guest1` и открыть в адресной строке `http://localhost:8080/api/admin/audit` →
вернётся **403 Forbidden** (страница/данные не показываются).

## Приложение. Почему всё работает «из коробки» без токенов

Система выдаёт JWT в **cookie** при входе на сайт. Пока вы залогинены на
`http://localhost:8080` в этой вкладке:

- переход по любой API-ссылке в **адресной строке** (GET) — авторизован автоматически;
- **Swagger UI** на том же адресе шлёт запросы с тем же cookie — кнопка «Authorize» не нужна;
- поэтому и «потыкать на сайте», и «потыкать в Swagger» работает без ручной возни с токеном.

Это подтверждено проверкой: запрос из Swagger/браузера проходит (201/204), а без cookie
тот же запрос отдаёт 401.
