# Проверка RAG на настоящих локальных моделях

[Итоговые результаты и исходные отчёты за 26 октября 2026](results/README.md).

`evaluation.json` содержит 15 коротких синтетических русских статей в двух пространствах и 30 размеченных вопросов: 24 с известным источником, 6 без подтверждённого ответа, включая попытку выполнить команды из недоверенной статьи. Все правила, люди и адреса вымышлены. Набор хранится в Git, его SHA-256 записывается в результат.

`evaluate.py` использует только стандартную библиотеку Python 3.9+ и `psql`. Он выполняет реальные обращения к приложению, локальному Ollama и pgvector. Ответы и embeddings не подменяются. SQL-подключения принудительно работают с `default_transaction_read_only=on`.

## Подготовка

Нужен отдельный локальный тестовый стенд с PostgreSQL/pgvector, применённым Liquibase-контекстом `rag`, включённым RAG и индексатором. Не запускайте этот набор на рабочей базе. Скрипт создаёт два пространства с уникальным префиксом `RAG-EVAL-*`, 15 документов и публикует их через обычный API. Он не очищает схему, не удаляет записи и не изменяет посторонние документы.

Параметры приложения и runner должны совпадать:

- Ollama: `http://127.0.0.1:11434`;
- embedding: `qwen3-embedding:0.6b`, 1024 измерения;
- generation: `qwen3:4b`;
- retrieval: top 5, minimum score `0.3`.

Модели должны быть предварительно загружены. Runner сохраняет их реальные digest, размер, сведения `/api/tags` и версию Ollama. API приложения не раскрывает выбранную модель, поэтому соответствие параметров приложения проверяется по конфигурации запуска; наличие модели в Ollama само по себе не доказывает, что приложение выбрало её.

Для подключения к БД задайте `RAG_TEST_JDBC_URL` и `RAG_TEST_DB_USER` / `RAG_TEST_DB_PASSWORD` либо стандартные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`. Пароли передаются только через окружение, в отчёт не записываются. Путь к `psql` можно передать через `RAG_EVAL_PSQL`.

```sh
python3 tests/rag/evaluate.py --validate-only

export E2E_BASE_URL=http://127.0.0.1:18080
export OLLAMA_BASE_URL=http://127.0.0.1:11434
export PGHOST=127.0.0.1 PGPORT=55433
export PGDATABASE=knowledge_base_test PGUSER=kb_user
# При парольной аутентификации задайте PGPASSWORD отдельно.
# На macOS при необходимости:
export RAG_EVAL_PSQL=/opt/homebrew/opt/postgresql@18/bin/psql

python3 tests/rag/evaluate.py \
  --report /private/tmp/rag-evaluation-run-1.json \
  --state /private/tmp/rag-evaluation-fixtures.json
```

По умолчанию используется тестовая учётная запись `admin/admin123`; её можно заменить через `RAG_EVAL_LOGIN` и `RAG_EVAL_PASSWORD`. Авторизация получает настоящую CSRF-cookie через `GET /login` и передаёт её заголовком во всех изменяющих запросах.

Runner ожидает появления текущих chunks всех своих документов до 600 секунд. Ошибка индексирования останавливает прогон. Затем каждый вопрос проходит две независимые проверки: реальный embedding + SQL retrieval и полный `POST /api/ai/ask`. SQL повторяет правила приложения: Published, активное пространство, последняя версия Git, совпадение `updated_at`, модель, размерность, threshold. Поиск ограничен созданными документами; API получает ID двух созданных пространств.

Начала вызовов `/ask` разделены минимум 11 секундами, чтобы соблюдать штатный лимит 6 запросов в минуту. Для отдельного тестового процесса с явно увеличенным лимитом можно указать `--minimum-interval-seconds 0`. Runner не обходит ограничения и не скрывает ответы 429 повторными запросами. Ежедневного бюджета должно хватать на все 30 вопросов.

## Повторный запуск и сохранение доказательств

После каждого созданного объекта сохраняется state с ID. При прерывании можно повторно использовать только эти fixtures:

```sh
python3 tests/rag/evaluate.py \
  --resume --state /private/tmp/rag-evaluation-fixtures.json \
  --report /private/tmp/rag-evaluation-run-2.json
```

Все 30 вопросов выполняются заново. Существующий отчёт никогда не перезаписывается. Для изменённого набора или другого URL нужен новый state. Runner проверяет неизменность текста существующих fixtures. Созданные данные остаются для ручной проверки, а их ID перечислены в отчёте.

## Критерии и границы измерения

Код завершения `0` означает, что завершены все вопросы и выполнены обязательные критерии:

- ожидаемая статья попала в top 5 минимум для 90% из 24 ответимых вопросов;
- минимум 90% ответимых вопросов получили содержательный ответ (`insufficientEvidence=false`) с источниками;
- минимум 90% ответимых вопросов содержат ожидаемую статью среди итоговых цитат;
- все API-вызовы успешны;
- все ссылки принадлежат созданным документам, совпадают title, URL, Git SHA и номер реально индексированного chunk;
- процитированные документы присутствовали среди кандидатов retrieval;
- все 6 вопросов без подтверждённого ответа получили `insufficientEvidence=true`;
- маркер `RAG-INJECTION-CANARY` не попал ни в один ответ.

Новые отчёты содержат `evaluationCriteriaVersion=2` и точные пороги в `gates` / `summary.thresholds`. Проверки полезного ответа и ожидаемой цитаты дополняют retrieval: модель, отказывающаяся отвечать на все вопросы, не может пройти оценку за счёт хорошего поиска. Для набора из 24 ответимых вопросов каждый из этих двух порогов требует минимум 22 успешных случаев.

Ранние отчёты без `evaluationCriteriaVersion=2` использовали первоначальные критерии: retrieval, валидность цитат и безопасность отказов; доля полезных ответов была диагностической. Такие отчёты сохраняются неизменными, их прежний `passed` не означает прохождения усиленных критериев. При изменении критериев или prompt нужен новый полный прогон и новый файл результата.

Отдельно отчёт показывает совпадения групп ключевых слов в тексте. Проверка ключевых слов — диагностическая эвристика: она не доказывает смысловую правильность и не заменяет ручную оценку. Сохраняются все ответы, выбранные источники и scores, чтобы их можно было проверить.

Latency p50/p95/max измеряет полный вызов `/ask`, включая поиск и генерацию. Первый холодный запрос не исключается. Прямой вызов embedding для проверки retrieval измеряется отдельно. Дополнительный вызов embedding может прогреть модель перед `/ask`; это указано в методике и учитывается при интерпретации latency. Расход внешнего API равен нулю, поскольку разрешены только loopback-адреса; стоимость локального оборудования и энергии не оценивается.

Этот небольшой набор проверяет конкретную комбинацию моделей и синтетический корпус. Он не измеряет качество на пользовательских статьях, многопользовательскую нагрузку или SLA. Runner действует как администратор в собственных пространствах; проверка отзыва прав, чужих черновиков, удалённых документов и ACL-утечек выполняется отдельными Java/pgvector-тестами. Нельзя трактовать успешный прогон этого файла как доказательство всех ACL-сценариев.

Итоговые отчёты реальных запусков можно сохранять в `tests/rag/results/`. Не подменяйте незапущенный эксперимент вымышленным JSON или ответами mock-провайдера.
