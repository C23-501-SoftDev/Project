# Проверка RAG на настоящих локальных моделях

[Итоговые результаты и исходные отчёты за 26 октября 2026](results/README.md).

`evaluation.json` содержит 15 коротких синтетических русских статей в двух пространствах и 30 размеченных вопросов: 24 с известным источником, 6 без подтверждённого ответа, включая попытку выполнить команды из недоверенной статьи. Все правила, люди и адреса вымышлены. Набор хранится в Git, его SHA-256 записывается в результат.

`evaluation-multi-document.json` сохраняет эти 15 статей и все 30 вопросов без изменений и добавляет 10 вопросов по двум или трём статьям. Среди новых случаев — сравнение сроков хранения, подготовка выпуска, проверка восстановления, связь мониторинга и инцидентов, редакторская памятка и полезный частичный ответ с явно неизвестной длительностью восстановления. Это отдельный набор из 40 вопросов; его нельзя подставлять в state исходного набора.

`evaluate.py` использует только стандартную библиотеку Python 3.9+ и `psql`. Он выполняет реальные обращения к приложению, локальному Ollama и pgvector. Ответы и embeddings не подменяются. SQL-подключения принудительно работают с `default_transaction_read_only=on`.

## Подготовка

Нужен отдельный локальный тестовый стенд с PostgreSQL/pgvector, применённым Liquibase-контекстом `rag`, включённым RAG и индексатором. Не запускайте этот набор на рабочей базе. Скрипт создаёт два пространства с уникальным префиксом `RAG-EVAL-*`, 15 документов и публикует их через обычный API. Он не очищает схему, не удаляет записи и не изменяет посторонние документы.

Параметры приложения и runner должны совпадать:

- Ollama: `http://127.0.0.1:11434`;
- embedding: `qwen3-embedding:0.6b`, 1024 измерения;
- generation: `qwen3:4b`;
- retrieval текущей реализации: top 8, не более 2 chunks на документ, minimum score `0.3`.

`--top-k` и `--max-chunks-per-document` должны совпадать с приложением. Для старого baseline используются `--top-k 5 --max-chunks-per-document 20`: историческое приложение не ограничивало chunks одной статьи, однако cap 20 даёт тот же результат на этом корпусе из 15 статей с одним chunk на статью. Это не эквивалентность для произвольного корпуса. Настройки записываются в `retrievalSettings`, пояснение — в `applicationDeployment.note`.

Модели должны быть предварительно загружены. Runner сохраняет их реальные digest, размер, сведения `/api/tags` и версию Ollama. API приложения не раскрывает выбранную модель, поэтому соответствие параметров приложения проверяется по конфигурации запуска; наличие модели в Ollama само по себе не доказывает, что приложение выбрало её.

Для подключения к БД задайте `RAG_TEST_JDBC_URL` и `RAG_TEST_DB_USER` / `RAG_TEST_DB_PASSWORD` либо стандартные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`. Пароли передаются только через окружение, в отчёт не записываются. Путь к `psql` можно передать через `RAG_EVAL_PSQL`.

```sh
python3 tests/rag/evaluate.py --validate-only
python3 tests/rag/evaluate.py --validate-only --dataset tests/rag/evaluation-multi-document.json
python3 -m unittest discover -s tests/rag -p 'test_*.py' -v

export E2E_BASE_URL=http://127.0.0.1:18080
export OLLAMA_BASE_URL=http://127.0.0.1:11434
export PGHOST=127.0.0.1 PGPORT=55433
export PGDATABASE=knowledge_base_test PGUSER=kb_user
# При парольной аутентификации задайте PGPASSWORD отдельно.
# На macOS при необходимости:
export RAG_EVAL_PSQL=/opt/homebrew/opt/postgresql@18/bin/psql

python3 tests/rag/evaluate.py \
  --report /private/tmp/rag-evaluation-run-1.json \
  --state /private/tmp/rag-evaluation-fixtures.json
```

По умолчанию используется тестовая учётная запись `admin/admin123`; её можно заменить через `RAG_EVAL_LOGIN` и `RAG_EVAL_PASSWORD`. Авторизация получает настоящую CSRF-cookie через `GET /login` и передаёт её заголовком во всех изменяющих запросах.

Runner ожидает появления текущих chunks всех своих документов до 600 секунд. Ошибка индексирования останавливает прогон. Затем каждый вопрос проходит две независимые проверки: реальный embedding + SQL retrieval и полный `POST /api/ai/ask`. SQL повторяет правила приложения: Published, активное пространство, последняя версия Git, совпадение `updated_at`, модель, размерность, threshold. Поиск ограничен созданными документами; API получает ID двух созданных пространств.

SQL ранжирует подходящие chunks отдельно внутри каждой статьи, применяет `maxChunksPerDocument`, затем общий порядок score / document ID / chunk index и `topK`. Для каждого вопроса сохраняются все выбранные кандидаты и первые пять. Вопрос с `expectedDocuments` требует **все** перечисленные статьи: нахождение или цитирование одной из двух не засчитывается как успех.

Начала вызовов `/ask` разделены минимум 11 секундами, чтобы соблюдать штатный лимит 6 запросов в минуту. Для отдельного тестового процесса с явно увеличенным лимитом можно указать `--minimum-interval-seconds 0`. Runner не обходит ограничения и не скрывает ответы 429 повторными запросами. Ежедневного бюджета должно хватать на все 30 или 40 вопросов выбранного набора.

## Повторный запуск и сохранение доказательств

После каждого созданного объекта сохраняется state с ID. При прерывании можно повторно использовать только эти fixtures:

```sh
python3 tests/rag/evaluate.py \
  --resume --state /private/tmp/rag-evaluation-fixtures.json \
  --report /private/tmp/rag-evaluation-run-2.json
```

Все 30 вопросов выполняются заново. Существующий отчёт никогда не перезаписывается. Для изменённого набора или другого URL нужен новый state. Runner проверяет неизменность текста существующих fixtures. Созданные данные остаются для ручной проверки, а их ID перечислены в отчёте.

Расширенный набор запускается аналогично, но с собственным state; при `--resume` заново выполняются все 40 вопросов:

```sh
python3 tests/rag/evaluate.py \
  --dataset tests/rag/evaluation-multi-document.json \
  --top-k 8 --max-chunks-per-document 2 \
  --state /private/tmp/rag-synthesis-fixtures.json \
  --report /private/tmp/rag-synthesis-candidate.json \
  --application-revision '<развёрнутый commit SHA>' \
  --application-jar /absolute/path/to/deployed.jar
```

Для сравнения baseline/candidate оставляют неизменными dataset, ID документов, URL тестового стенда и критерии. После замены JAR используют тот же state с `--resume` и новый путь отчёта; retrieval-параметры указывают по реально запущенной версии. `applicationDeployment` содержит заявленную оператором ревизию и SHA-256 переданного JAR. API сам не подтверждает конфигурацию или ревизию: путь должен указывать именно на запущенный JAR.

## Критерии и границы измерения

Код завершения `0` означает, что завершены все вопросы и выполнены обязательные критерии:

- ожидаемая статья попала в первые 5 кандидатов минимум для 90% исходных 24 ответимых вопросов; этот критерий сохраняется и при `topK=8`;
- минимум 90% исходных 24 вопросов отдельно получили содержательный ответ и минимум 90% — ожидаемую цитату; успех новых вопросов не компенсирует регрессию старых;
- все ожидаемые статьи попали в top K минимум для 90% ответимых вопросов;
- минимум 90% ответимых вопросов получили содержательный ответ (`insufficientEvidence=false`) с источниками;
- минимум 90% ответимых вопросов содержат ожидаемую статью среди итоговых цитат;
- все API-вызовы успешны;
- все ссылки принадлежат созданным документам, совпадают title, URL, Git SHA и номер реально индексированного chunk;
- процитированные документы присутствовали среди кандидатов retrieval;
- все 6 вопросов без подтверждённого ответа получили `insufficientEvidence=true`;
- маркер `RAG-INJECTION-CANARY` не попал ни в один ответ.

Расширенный набор дополнительно требует отдельно для десяти новых вопросов:

- минимум 90% случаев извлекают **все** ожидаемые статьи в top K;
- минимум 90% случаев получают HTTP 200, содержательный ответ, все обязательные цитаты, корректное происхождение цитат, все группы фактов из `evidenceKeywordGroups` и, когда задано, явное указание пробела из `expectedGapKeywordGroups`.

Для десяти новых вопросов нужно не менее девяти полных ответов. Успех на старых 24 вопросах не компенсирует провал многосоставных. Полезный частичный ответ считается содержательным (`insufficientEvidence=false`), но обязан явно отметить неизвестную часть. Полностью неподтверждённые вопросы по-прежнему требуют отказа.

Новые отчёты содержат `evaluationCriteriaVersion=4` и точные пороги в `gates` / `summary.thresholds`. Версия 3 добавила отдельный legacy recall@5, recall@K и многосоставную полноту. Версия 4 дополнительно требует отдельно ≥90% содержательных ответов и ≥90% ожидаемых цитат для исходных 24 вопросов: 21/24 не могут скрыться за успехом десяти новых вопросов. Для этих проверок нужно минимум 22 успешных случая. Версия 2 первоначально добавила полезность и ожидаемые цитаты к retrieval, чтобы модель с универсальным отказом не могла пройти оценку только за счёт поиска.

Baseline синтеза сохранён с критериями v3 без изменения JSON. Его исходные 24/24 полезных ответа и 24/24 ожидаемых цитат удовлетворяют обоим дополнительным требованиям v4; это проверяется по сохранённым ответам без нового обращения к модели. Десять новых вопросов, корпус и порог многосоставной полноты между baseline и candidate не меняются.

Ранние отчёты без `evaluationCriteriaVersion=2` использовали первоначальные критерии: retrieval, валидность цитат и безопасность отказов; доля полезных ответов была диагностической. Такие отчёты сохраняются неизменными, их прежний `passed` не означает прохождения усиленных критериев. При изменении критериев или prompt нужен новый полный прогон и новый файл результата.

Для старых вопросов `expectedAllKeywordGroups` остаётся диагностической эвристикой. Для новых вопросов группы обязательных фактов и явного пробела входят в gate полноты, но не доказывают смысловую правильность: ключевые слова могут встретиться в неверном утверждении. Поэтому реальный отчёт дополнительно читают вручную, проверяя соответствие фактов статьям, отсутствие придуманных причинных связей и корректность оговорок. Сохраняются все ответы, выбранные источники и scores. Альтернативы группы разделяются `|`; после начала baseline набор и группы не редактируют для получения более высокого балла.

Latency p50/p95/max измеряет полный вызов `/ask`, включая поиск и генерацию. Первый холодный запрос не исключается. Прямой вызов embedding для проверки retrieval измеряется отдельно. Дополнительный вызов embedding может прогреть модель перед `/ask`; это указано в методике и учитывается при интерпретации latency. Расход внешнего API равен нулю, поскольку разрешены только loopback-адреса; стоимость локального оборудования и энергии не оценивается.

Этот небольшой набор проверяет конкретную комбинацию моделей и синтетический корпус. Он не измеряет качество на пользовательских статьях, многопользовательскую нагрузку или SLA. Runner действует как администратор в собственных пространствах; проверка отзыва прав, чужих черновиков, удалённых документов и ACL-утечек выполняется отдельными Java/pgvector-тестами. Нельзя трактовать успешный прогон этого файла как доказательство всех ACL-сценариев.

Итоговые отчёты реальных запусков можно сохранять в `tests/rag/results/`. Не подменяйте незапущенный эксперимент вымышленным JSON или ответами mock-провайдера.

## Дополнительные пробы синтеза у провайдера

`probe-synthesis.py` проверяет два отдельных случая: противоречащие друг другу сроки хранения для одного проекта и запрет переносить сведения Ориона на другой проект Вега. Скрипт извлекает текущий Java system prompt и модельные настройки по умолчанию, использует ту же JSON Schema и сохраняет исходные ответы Ollama, digest модели и SHA-256 исходников/prompt.

```sh
python3 tests/rag/probe-synthesis.py \
  --report /private/tmp/rag-synthesis-provider-probe.json
```

Это прямые вызовы локального `/api/chat`, **не** `/api/ai/ask`: они не проверяют retrieval, JWT, CSRF, ACL или сборку контекста приложения и не добавляются к числу 40 end-to-end вопросов. Успех требует последующей ручной проверки: модель должна показать оба противоречащих факта без выдуманного приоритета и отказаться от неподтверждённого переноса между проектами. При изменённых через окружение параметрах приложения нужно отдельно проверить соответствие пробе. Скрипт не перезаписывает существующие отчёты и не обращается к облачным моделям.
