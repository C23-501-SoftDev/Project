## Context

Страница администрирования пространств уже умеет загружать список через `/api/admin/spaces`, но порядок фиксирован на стороне сервера и не соответствует ожидаемому естественному порядку. Для таблицы в админке требуется сортировка по каждому видимому столбцу.

## Goals / Non-Goals

**Goals:**
- Сделать сортировку таблицы пространств управляемой из UI.
- Поддержать сортировку по всем отображаемым полям, кроме действий.
- Сохранить пагинацию и фильтр статуса.

**Non-Goals:**
- Не менять бизнес-логику создания, редактирования или удаления пространств.
- Не вводить отдельный экран настройки сортировки.

## Decisions

### 1. Источник сортировки
**Решение:** сортировка управляется параметрами `sortBy` и `sortDir` в запросе к `/api/admin/spaces`.
**Обоснование:** это сохраняет единый API для таблицы и позволяет фронтенду управлять сортировкой без дополнительных эндпоинтов.

### 2. Кликабельные заголовки
**Решение:** все заголовки, кроме `Actions`, становятся интерактивными и переключают сортировку по соответствующему столбцу.
**Обоснование:** это соответствует ожиданиям пользователя от табличного UI.

### 3. Порядок по умолчанию
**Решение:** использовать естественный порядок по умолчанию, `createdAt asc`.
**Обоснование:** текущее поведение воспринимается как обратное и мешает просмотру списка.

### 4. Поля сортировки
**Решение:** поддержать сортировку по `id`, `name`, `description`, `ownerLogin`, `status`, `createdAt`, `updatedAt`.
**Обоснование:** это покрывает все видимые колонки таблицы и не требует отдельного интерфейса.

## Risks / Trade-offs

- **[Risk]** Сортировка по `ownerLogin` требует дополнительных вычислений на сервере. → **Mitigation**: использовать существующий маппинг пространства в response и сортировать уже отображаемые строки.
- **[Risk]** Добавление интерактивности в заголовки может ухудшить доступность. → **Mitigation**: сохранить семантику таблицы и добавить явные состояния сортировки.
