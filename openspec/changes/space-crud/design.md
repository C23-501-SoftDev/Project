## Context

Система уже имеет базовую структуру для работы с пространствами (`Space`), но она ограничена только созданием и получением списка. Отсутствуют механизмы обновления данных и удаления. Архитектура проекта требует строгого разделения на слои (Clean Architecture).

## Goals / Non-Goals

**Goals:**
- Реализовать полный цикл CRUD для `Space` на уровне API администратора.
- Обеспечить автоматическое назначение прав `OWNER` при смене владельца через CRUD.
- Реализовать каскадное удаление (или проверку наличия зависимых документов) при удалении пространства.
- Поддерживать аудит-поля `createdAt`/`updatedAt`.

**Non-Goals:**
- Реализация UI (только бэкенд API).
- Изменение логики прав доступа (кроме автоматического назначения при создании/смене владельца).

## Decisions

### 1. Обработка удаления (Soft vs Hard)
**Решение:** Hard delete для сущности `Space` в БД, так как это административная операция.
**Обоснование:** В текущей модели не предусмотрено корзины для пространств. Удаление пространства влечет за собой удаление всех связанных прав доступа (`SpacePermission`). Документы внутри пространства должны быть либо удалены, либо перемещены (в рамках данной задачи — блокировка удаления при наличии документов или их удаление, уточняется триггерами БД).

### 2. Смена владельца
**Решение:** При обновлении `ownerId` в `SpaceService`, автоматически вызывается `PermissionService` для:
1. Удаления старой записи `OWNER` для данного пространства.
2. Создания новой записи `OWNER` для нового владельца.
**Альтернатива:** Оставить управление правами полностью на совести админа. 
**Выбор:** Автоматизация в сервисе гарантирует консистентность, требуемую в US.

### 3. Схема API
- `GET /api/admin/spaces/{id}`: Возвращает `SpaceResponse`.
- `PUT /api/admin/spaces/{id}`: Принимает `UpdateSpaceRequest`.
- `DELETE /api/admin/spaces/{id}`: Возвращает 204 No Content.

### 4. Изменения в слоях
- **Domain**: Добавление метода `updateInfo(name, description, ownerId)` в модель `Space`.
- **Infrastructure**: Добавление `deleteById` и `findById` в `SpaceJpaRepository`.
- **Interfaces**: Новые DTO `UpdateSpaceRequest`.

## Risks / Trade-offs

- **[Risk]** Удаление пространства с большим количеством документов. → **Mitigation**: Использовать транзакции и проверить наличие внешних ключей в БД. Если БД настроена на `ON DELETE CASCADE`, проблем быть не должно.
- **[Risk]** Дублирование имен при обновлении. → **Mitigation**: Валидация в сервисе через `spaceRepository.existsByNameAndIdNot(...)`.
