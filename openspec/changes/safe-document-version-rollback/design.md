## Context

См. `proposal.md`. В проекте уже есть неизменяемые Git-снимки опубликованного документа, таблица `versions` с SHA и путём файла для каждой версии, `GET /api/documents/{id}/versions` и JGit-операции чтения файла из дерева конкретного коммита. `JGitDocumentContentRepository` сериализует операции сохранения снимка, а `DocumentService.updateDocument` применяет порядок Git → БД и журналирует orphan SHA при ошибке persistence.

Откат является новым изменяющим действием: старый коммит нельзя checkout/reset-ить как текущий `HEAD`, поскольку это стирает или перемещает общую историю локального репозитория и нарушает параллельные операции с другими документами.

## Goals / Non-Goals

**Goals:**

- Восстановить текст выбранной, принадлежащей документу Git-версии как новый снимок с новым SHA.
- После Git-коммита обновить DB-индекс документа и создать новую строку `versions` в одной DB-транзакции.
- Сохранить действующие модель прав, Git-lock и гарантии невмешательства в историю.

**Non-Goals:**

- Переписывание Git-истории (`reset`, `rebase`, force-push) или переключение рабочего дерева на старый `HEAD`.
- Восстановление метаданных структуры документа (`title`, `parentDocumentId`, `status`), вложений, других документов либо целого репозитория; откат восстанавливает текст файла.
- Разрешение конфликтов, branch/remote synchronization, rollback черновика или удалённого документа.

## Decisions

### 1. Создать новый снимок вместо Git revert или checkout

`POST /api/documents/{id}/versions/{gitHash}/restore` принимает только SHA из `versions` данного документа. Application service читает blob документа из tree выбранного commit через новый метод порта `readDocumentVersion(path, gitHash)`; затем использует существующий атомарный `saveDocumentSnapshot` для записи этого текста вместе с metadata sidecar в новый commit с автором текущего редактора.

Выбрано создание снимка, а не `git revert`: revert применяет обратный diff конкретного commit относительно его родителя и не гарантирует состояние произвольно выбранной старой версии. `checkout`/`reset` меняют `HEAD` и рабочее дерево репозитория. Создание снимка напрямую удовлетворяет критерию «старая версия как новая текущая» и безопасно для совместного репозитория.

### 2. Граница доступа и валидность цели до чтения Git

Controller применяет `@PreAuthorize` с `canEdit` для пространства документа и проверяет CSRF существующим Spring Security механизмом. Service валидирует формат SHA, загружает документ и находит версию через `findByDocumentIdAndGitHash`; только после этого он обращается к JGit. Ошибки: malformed SHA → 400, документ/незарегистрированная версия → 404, отсутствие EDIT → 403.

Это сохраняет текущую защиту diff: SHA стороннего документа не становится способом чтения его содержимого. Альтернатива — передавать произвольный SHA в JGit — отклонена из-за раскрытия данных и обхода журнала версий.

### 3. Согласование Git и DB-индекса

Операция в `DocumentVersionService` (или выделенном rollback use case) использует DB `@Transactional`, а JGit adapter сохраняет синхронизацию на уровне репозитория. Порядок: валидация → чтение целевой версии → новый Git-снимок → обновление timestamp/индексируемого состояния `Document` → сохранение новой `DocumentVersion` с новым SHA → audit/event после commit.

Единой ACID-транзакции между Git и PostgreSQL нет. При Git-ошибке БД остаётся без изменений. При DB-ошибке DB-транзакция откатывается, SHA orphan commit журналируется; Git rollback запрещён, чтобы не удалить параллельный commit. Это согласовано с существующей политикой `updateDocument`.

### 4. REST/UI-контракт и идемпотентность

Успешный endpoint возвращает DTO созданной версии (`gitHash`, `comment`, `createdAt`) с `201 Created`; commit message однозначно указывает восстановленный SHA. Повторное восстановление допускается и создаёт отдельную audit-visible запись: это намеренное действие, поэтому сервер не считает его no-op. Кнопка «Откат версии» в редакторе открывает `document-history.html` в rollback-режиме: слева выбрана и заблокирована текущая версия, справа редактор выбирает целевую версию, видит diff и явно запускает «Сохранить». Запрос передаёт CSRF header, а после успеха пользователь возвращается в редактор уже с восстановленным текстом.

### 5. Предполагаемые участки кода

| Layer | Planned changes |
| --- | --- |
| domain | Метод чтения содержимого версии в `DocumentContentRepository`; модель/результат rollback при необходимости. |
| application | `DocumentVersionService`/новый use case: validation, Git → DB orchestration, orphan logging, audit/event. |
| infrastructure | JGit чтение файла из tree по SHA с path validation; без изменения HEAD. `DocumentRepository` и `DocumentVersionRepository` сохраняют переиндексированный документ и новую версию. |
| interfaces | `DocumentVersionController`, response DTO, exception mapping/OpenAPI; `document-history.html`, JS/CSS. |
| db/docs | Новая схема не требуется; `BACKTRACKER.md` и feature registry отражают endpoint. |

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| Git и PostgreSQL не образуют общую транзакцию | Git-first, DB rollback, orphan SHA в логах и без небезопасного Git reset. |
| SHA из чужого документа | Проверять регистрацию SHA в рамках `documentId` до JGit. |
| Параллельное сохранение/откат | Сериализация JGit операций и SHA из возвращённого `RevCommit`, а не глобального `HEAD`. |
| Восстановление старых структуры/статуса может сломать иерархию | Откатывать только текст; metadata sidecar нового snapshot отражает текущие DB-атрибуты. |
| Повторный запрос создаёт лишнюю версию | Откат доступен только через отдельный режим с просмотром diff и явной кнопкой «Сохранить»; каждое действие прозрачно остаётся в истории. |

## Migration Plan

1. Развернуть backend и UI без Liquibase migration: существующие `versions` и metadata sidecars используются как источник зарегистрированных версий.
2. Выполнить проверку на тестовом Git-репозитории: восстановление старой версии создаёт новый SHA, затем история и чтение текущего файла согласованы.
3. При откате релиза отключить/удалить endpoint и кнопку UI; созданные Git-коммиты и строки `versions` сохраняются и не требуют data migration.
