## Context

Управление группами реализовано в изменении `user-group-management`. Теперь нужно управлять составом групп: связывать пользователей с группами и разрывать эти связи. Схема БД (`user_group_members`) подготовлена миграцией Liquibase 015 с уникальностью пары `(group_id, user_id)` и каскадным удалением по FK. Реализация выполняется по той же чистой архитектуре, что и остальные модули.

## Goals / Non-Goals

**Goals:**
- Реализовать добавление и удаление участника группы, а также просмотр состава.
- Гарантировать корректные коды ошибок: 404 (нет группы/пользователя/членства), 409 (повторное добавление).
- Сделать удаление группы детерминированным — явно очищать состав на уровне сервиса.

**Non-Goals:**
- Назначение прав группам на пространства (`space_group_permissions`) — отдельная user story US4.2.3.
- Эффективное вычисление эффективных прав пользователя с учётом групп — вне скоупа.
- UI администратора (только бэкенд API).

## Decisions

### 1. Связующая сущность по образцу SpacePermission
**Решение:** `UserGroupMemberJpaEntity` хранит `group_id`/`user_id` как простые `Long` (без `@ManyToOne`), как `SpacePermissionJpaEntity`.
**Обоснование:** единообразие, отсутствие N+1, простота. Данные пользователя для ответа подтягиваются в `RestDtoMapper`.

### 2. Валидация при добавлении
**Решение:** проверяем существование группы (404 `GroupNotFoundException`), активного пользователя (404 `UserNotFoundException`) и отсутствие дубликата (409 `ConflictException`).
**Обоснование:** соответствует критериям приёмки US4.1.9 и поведению модуля прав.

### 3. Удаление участника
**Решение:** если членства нет — 404 `GroupMembershipNotFoundException`; иначе удаляем (204 No Content).
**Обоснование:** явная обработка ошибок; идемпотентное «тихое» удаление скрыло бы опечатки в ID.

### 4. Удаление группы очищает состав явно
**Решение:** `UserGroupService.deleteGroup` вызывает `memberRepository.deleteByGroupId` перед удалением группы.
**Обоснование:** FK-каскад существует в PostgreSQL (changelog 015), но отсутствует в тестовой H2-схеме (колонки — простые `Long`). Явная очистка делает поведение детерминированным и реализует US4.1.8 Сценарий 2 при наличии участников.

### 5. Схема API
- `GET /api/admin/groups/{groupId}/members` — список участников (`GroupMemberResponse` с login/email/role).
- `POST /api/admin/groups/{groupId}/members` — добавить (`AddGroupMemberRequest` с `userId`).
- `DELETE /api/admin/groups/{groupId}/members/{userId}` — удалить (204).

Доступ только для ADMIN (как и весь `AdminGroupController`).

## Risks / Trade-offs

- **[Risk]** Гонка при одновременном добавлении одного пользователя дважды. → **Mitigation**: уникальное ограничение БД `uq_user_group_members` не даст создать дубликат; сервисная проверка предотвращает его в штатном сценарии.
- **[Trade-off]** Состав группы возвращается без пагинации. → Приемлемо для административных сценариев; при росте можно добавить пагинацию позже.
