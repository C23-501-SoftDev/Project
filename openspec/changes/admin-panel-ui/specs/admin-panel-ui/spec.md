# admin-panel-ui Specification

## ADDED Requirements

### Requirement: Admin Users Page UI
Система ДОЛЖНА (SHALL) предоставлять страницу `GET /admin/users`, которая отображает всех зарегистрированных пользователей в сортируемой таблице с колонками: ID, Login, Email, Roles, Status, Actions. Страница ДОЛЖНА (MUST) загружать данные через fetch в `/api/admin/users` с поддержкой пагинации. Страница ДОЛЖНА (SHALL) включать: поле поиска по Login/Email, role filter checkboxes (Admin/Editor/Reader), кнопку Create User и кнопки действий для каждого пользователя (Edit, Delete, Reset Password).

#### Scenario: Загрузка страницы с таблицей пользователей
- **WHEN** аутентифицированный администратор переходит на `/admin/users`
- **THEN** страница отображает `admin-layout.html` с контентом `admin-users.html` и запрашивает данные пользователей из `/api/admin/users?page=0&size=20`

#### Scenario: Поиск фильтрует пользователей по логину или email
- **WHEN** администратор вводит "admin" в поле поиска и нажимает Apply
- **THEN** таблица показывает только пользователей, чей логин или email содержит "admin" (регистронезависимый поиск по подстроке)

#### Scenario: Role filter показывает только соответствующих пользователей
- **WHEN** администратор устанавливает флажок "Editor" и нажимает Apply
- **THEN** таблица показывает только пользователей с role=EDITOR

#### Scenario: Пагинация переключает страницы пользователей
- **WHEN** администратор нажимает "Next" или выбирает страницу 2
- **THEN** система запрашивает `/api/admin/users?page=1&size=20` и обновляет таблицу

#### Scenario: Выбор количества на странице изменяет размер страницы
- **WHEN** администратор выбирает "50" из выпадающего списка
- **THEN** система запрашивает `/api/admin/users?page=0&size=50` и обновляет таблицу

#### Scenario: Сортировка столбцов переключает порядок сортировки
- **WHEN** администратор кликает на заголовок столбца "Login"
- **THEN** система запрашивает `/api/admin/users?sortBy=login&sortDir=asc` и обновляет таблицу отсортированными данными

### Requirement: Create User Modal
Система ДОЛЖНА (SHALL) предоставлять модальное окно, вызываемое кнопкой "Create User" на странице пользователей. Модальное окно ДОЛЖНО (SHALL) содержать поля: Login* (обязательное), Email* (обязательное), Password* (обязательное, минимум 6 символов), Role (select: READER/EDITOR/ADMIN, по умолчанию READER). Статус пользователя определяется бэкендом (по умолчанию Active). При отправке система ДОЛЖНА (SHALL) выполнить POST в `/api/admin/users` с `{ login, email, password, role }`. При успехе модальное окно закрывается, таблица обновляется и появляется уведомление toast.

#### Scenario: Успешное создание пользователя
- **WHEN** администратор заполняет все обязательные поля и нажимает Save
- **THEN** система выполняет POST в `/api/admin/users`, закрывает модальное окно, обновляет таблицу и показывает toast "User created"

#### Scenario: Ошибка валидации при дублировании логина
- **WHEN** администратор отправляет форму с уже существующим логином
- **THEN** модальное окно показывает сообщение об ошибке и не закрывается

#### Scenario: Ошибка валидации при коротком пароле
- **WHEN** администратор отправляет форму с паролем короче 6 символов
- **THEN** модальное окно показывает встроенную ошибку "Password must be at least 6 characters"

### Requirement: Edit User Modal
Система ДОЛЖНА (SHALL) предоставлять модальное окно, вызываемое кнопкой "Edit" для каждой строки пользователя. Модальное окно ДОЛЖНО (SHALL) быть предварительно заполнено текущими данными пользователя из `/api/admin/users/{id}`. Поля: Login (редактируемое), Email (редактируемое), Role (select). Поле Password опционально — пустое означает отсутствие изменений, заполненное означает сброс. При отправке система ДОЛЖНА (SHALL) выполнить PUT в `/api/admin/users/{id}` с `{ login, email, role }`. Если пароль указан, система ДОЛЖНА (SHALL) дополнительно выполнить PUT в `/api/admin/users/{id}/password`.

#### Scenario: Успешное обновление пользователя
- **WHEN** администратор изменяет email и нажимает Save
- **THEN** система выполняет PUT в `/api/admin/users/{id}`, закрывает модальное окно, обновляет таблицу и показывает toast "User updated"

#### Scenario: Сброс пароля через модальное окно редактирования
- **WHEN** администратор открывает модальное окно Edit, заполняет поле пароля и нажимает Save
- **THEN** система выполняет PUT в `/api/admin/users/{id}` для профиля и PUT в `/api/admin/users/{id}/password` для сброса пароля

### Requirement: Delete User Confirmation Modal
Система ДОЛЖНА (SHALL) предоставлять модальное окно подтверждения, вызываемое кнопкой "Delete" для каждой строки пользователя. Модальное окно ДОЛЖНО (SHALL) отображать логин пользователя и предупреждать, что удаление необратимо и не выполнится, если пользователь владеет документами или пространствами. При подтверждении система ДОЛЖНА (SHALL) выполнить DELETE `/api/admin/users/{id}`. При ошибке 409 Conflict модальное окно ДОЛЖНО (SHALL) показать причину конфликта. При успехе модальное окно закрывается, таблица обновляется и появляется toast.

#### Scenario: Успешное удаление пользователя
- **WHEN** администратор подтверждает удаление пользователя без связанных данных
- **THEN** система выполняет DELETE `/api/admin/users/{id}`, закрывает модальное окно, обновляет таблицу и показывает toast "User deleted"

#### Scenario: Удаление заблокировано внешними ключами
- **WHEN** администратор подтверждает удаление пользователя, владеющего документами
- **THEN** система отвечает 409, и модальное окно показывает "Cannot delete user: they are the author of documents. Reassign or delete documents first."

### Requirement: Admin Spaces Page UI
Система ДОЛЖНА (SHALL) предоставлять страницу `GET /admin/spaces`, отображающую все пространства документов в сортируемой таблице с колонками: ID, Name, Description, Owner, Status, Actions. Страница ДОЛЖНА (MUST) загружать данные через fetch в `/api/admin/spaces?page=0&size=20`. Страница ДОЛЖНА (SHALL) включать: кнопку Create Space, кнопку Grant Permission и кнопки действий для каждого пространства (Edit как заглушка, Delete как заглушка).

#### Scenario: Загрузка страницы с таблицей пространств
- **WHEN** аутентифицированный администратор переходит на `/admin/spaces`
- **THEN** страница отображает `admin-layout.html` с контентом `admin-spaces.html` и запрашивает данные из `/api/admin/spaces?page=0&size=20`

#### Scenario: Пагинация переключает страницы пространств
- **WHEN** администратор нажимает "Next" или меняет страницу
- **THEN** система запрашивает `/api/admin/spaces?page=1&size=20` и обновляет таблицу

### Requirement: Create Space Modal
Система ДОЛЖНА (SHALL) предоставлять модальное окно, вызываемое кнопкой "Create Space". Поля: Name* (обязательное, уникальное), Description (textarea, опционально), Owner (выпадающий список пользователей, опционально — по умолчанию текущий администратор), Status (select: Active/Inactive). При отправке система ДОЛЖНА (SHALL) выполнить POST в `/api/admin/spaces` с `{ name, description, ownerId }`.

#### Scenario: Успешное создание пространства
- **WHEN** администратор заполняет Name и нажимает Save
- **THEN** система выполняет POST в `/api/admin/spaces`, закрывает модальное окно, обновляет таблицу и показывает toast "Space created"

#### Scenario: Отклонение дублирующегося имени
- **WHEN** администратор отправляет уже существующее имя
- **THEN** модальное окно показывает ошибку "Space name is already taken"

### Requirement: Grant Space Permission
Система ДОЛЖНА (SHALL) предоставлять модальное окно, вызываемое кнопкой "Grant Permission" для каждой строки пространства. Модальное окно ДОЛЖНО (SHALL) содержать выпадающий список пользователей и селектор типа permission (READ/WRITE/OWNER). При отправке система ДОЛЖНА (SHALL) выполнить POST в `/api/admin/spaces/{spaceId}/permissions` с `{ userId, permissionType }`.

#### Scenario: Успешное предоставление прав
- **WHEN** администратор выбирает пользователя и тип permission, затем нажимает "Grant"
- **THEN** система выполняет POST в `/api/admin/spaces/{spaceId}/permissions`, закрывает модальное окно и показывает toast "Permission granted"

#### Scenario: Отклонение дублирующихся прав
- **WHEN** администратор предоставляет права, уже существующие для пользователя в этом пространстве
- **THEN** модальное окно показывает ошибку "This permission already exists"

### Requirement: Edit Space Stubs
Кнопка Edit Space для каждой строки пространства ДОЛЖНА (SHALL) показывать уведомление "Функция в разработке" (в разработке) вместо открытия модального окна. Backend endpoint `PUT /api/admin/spaces/{id}` ещё не реализован.

#### Scenario: Показана заглушка редактирования пространства
- **WHEN** администратор нажимает кнопку Edit для строки пространства
- **THEN** система показывает toast "Функция в разработке" и не выполняет API вызов

### Requirement: Delete Space Stubs
Кнопка Delete Space ДОЛЖНА (SHALL) показывать уведомление "Функция в разработке" (в разработке) вместо открытия модального окна подтверждения. Backend endpoint `DELETE /api/admin/spaces/{id}` ещё не реализован.

#### Scenario: Показана заглушка удаления пространства
- **WHEN** администратор нажимает кнопку Delete для строки пространства
- **THEN** система показывает toast "Функция в разработке" и не выполняет API вызов

### Requirement: Admin Settings Stub Page
Система ДОЛЖНА (SHALL) предоставлять страницу `GET /admin/settings`, отображающую сообщение "Функция в разработке" (Настройки в разработке) с иконкой. Страница ДОЛЖНА (SHALL) использовать `admin-layout.html` и выделять "Настройки" в sidebar.

#### Scenario: Администратор просматривает страницу настроек
- **WHEN** аутентифицированный администратор переходит на `/admin/settings`
- **THEN** страница отображается с сообщением "в разработке"

### Requirement: Admin Layout Updated with Settings Link
`admin-layout.html` sidebar ДОЛЖЕН (SHALL) включать ссылку "Настройки" (Settings), указывающую на `/admin/settings`. Ссылка ДОЛЖНА (SHALL) отображаться как активная, когда текущая страница `/admin/settings`.

#### Scenario: Sidebar показывает ссылку Настройки
- **WHEN** администратор просматривает любую страницу `/admin/*`
- **THEN** sidebar показывает ссылки: "Пользователи", "Пространства", "Настройки"

#### Scenario: Ссылка Настройки выделена на странице настроек
- **WHEN** администратор переходит на `/admin/settings`
- **THEN** ссылка "Настройки" имеет активный CSS-класс

### Requirement: Admin Common JavaScript Utilities
Система ДОЛЖНА (SHALL) предоставлять JavaScript-модуль `/static/js/admin-common.js`, экспортирующий утилитарные функции: `getCsrfToken()` (читает XSRF-TOKEN cookie), `adminFetch(url, options)` (обёртка fetch с CSRF-заголовком и обработкой ошибок), `showToast(message, type)` (показывает уведомление), `openModal(id)`, `closeModal(id)`, `escapeHtml(str)`.

#### Scenario: adminFetch включает CSRF-заголовок
- **WHEN** adminFetch вызывается с методом POST
- **THEN** запрос включает заголовок `X-XSRF-TOKEN` со значением из cookie

#### Scenario: adminFetch обрабатывает ошибку 403
- **WHEN** adminFetch получает ответ 403
- **THEN** система показывает toast "Access denied" и не выбрасывает исключение

#### Scenario: showToast показывает временное сообщение
- **WHEN** вызывается showToast("Saved", "success")
- **THEN** зелёное уведомление появляется в правом нижнем углу и автоматически скрывается через 2 секунды

### Requirement: Admin-Only Page Access
Все страницы `/admin/*` ДОЛЖНЫ (SHALL) быть доступны только пользователям с ролью ADMIN, что обеспечивается существующей `SecurityConfig.requestMatchers("/admin/**").hasRole("ADMIN")`. Пользователи без прав администратора ДОЛЖНЫ (SHALL) быть перенаправлены на страницу входа или получить 403.

#### Scenario: Администратор получает доступ к странице администрирования
- **WHEN** аутентифицированный администратор переходит на `/admin/users`
- **THEN** страница загружается нормально

#### Scenario: Редактору отказано в доступе к страницам администрирования
- **WHEN** аутентифицированный редактор переходит на `/admin/users`
- **THEN** система отвечает 403 Forbidden
