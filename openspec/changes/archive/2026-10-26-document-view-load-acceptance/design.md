## Context
US4.4.1 requires document display within two seconds under normal load. The prior one-user measurement is insufficient. The user explicitly selected 25 active users on 2026-10-26.
## Goals / Non-Goals
Verify the selected local workload with real PostgreSQL, Git content, JWT sessions and browser rendering. Do not claim production certification, unlimited capacity or RAG inference performance.
## Decisions
- Target `tests/performance` tooling; application controller/service/repository changes only if measured failures establish a bottleneck. No schema changes are initially required.
- Use a dedicated loopback app and database ending `_test`, gated by explicit test opt-in. Check app/database identity before seeding. Preserve fixture checkpoints and previous results.
- Corpus: 50 spaces with 100 metadata documents each, one space with 5000 documents, and at least ten real published Markdown targets created through the application and stored in Git. Metadata-only nodes are never opened as documents.
- Normal profiles: distributed spaces and one large space, each 25 separate READER sessions (24 HTTP workers plus one browser), at least 60 seconds. HTTP workers wait one second after each completed cycle; the browser probes continuously with browserThinkTimeMs=0. Workload version 2 reproduces six HTTP endpoints: SSR, document JSON, document permissions, attachments, current-space tree and the header create-permission request `/api/spaces?requiredAccess=WRITE&size=1`. Fixture readers have no write grants, so the header response must be an empty array.
- Browser: real Chromium with CDP 100ms latency, 20Mbps down and 5Mbps up; at least 20 document navigations while background load is active, split between fresh browser contexts and repeat visits. Fresh browser cache is not a cold JVM. HTTP workers stay on loopback without injected latency; report this distinction.
- Browser listeners remain active through header-response validation and bounded draining of all tracked navigation requests, with 100ms network quiescence. Late response/script failures and requests still pending after the ten-second drain timeout fail the sample, including navigation failure paths. Content-ready timing remains captured at rendered article visibility plus two animation frames; draining is reported separately in total duration.
- Fixed normal gates before the first run: zero response/render errors, sufficient samples, endpoint and content-chain p95 <=2000ms, and every observed browser content-ready navigation <=2000ms. Record p50/p95/max, requests/second, actual duration, cold/repeat results and tree completion separately. No outlier removal or retries hiding failures.
- Stress: 50 active users, same large-space workflow and duration. Report results separately; a stress failure does not redefine the agreed 25-user normal profile.
- Preserve the first five-endpoint run as baseline evidence. Version 2 adds real UI coverage and applies the existing endpoint p95 limit to the added header request; it does not weaken original gates. Final acceptance requires version 2.
## Risks / Trade-offs
Local browser, JVM and PostgreSQL share a host, unlike production. Record environment and workload; avoid concurrent builds/model inference during measurements. A single large tree may expose SQL, HTML or DOM scaling problems; fix demonstrated bottlenecks without reducing fixtures or weakening gates. Real deployment hardware and network still require their own acceptance.
## Migration Plan
No production migration. Publish runner, evidence and instructions; retain old one-user results as historical observations.

## Measured bottleneck and implementation decision
The first run failed in the 5001-node tree: HTTP tree p95 was 7056ms, while article content-ready stayed below 571ms. The flat fixture does not exercise recursive template inclusion; bulk repository loading and linear tree assembly already avoid N+1. A separate cache/SpEL-compiler diagnostic did not remove the latency. Replace only the tree fragment's Thymeleaf processing with a stateless, escaped HTML renderer in the interfaces layer. Keep the existing endpoint, visible-node service, URL and DOM contracts, order, selected node, drag/drop attributes and `Cache-Control: no-store`. Use an iterative traversal so rendering depth does not consume the Java call stack. Do not cache authorization-dependent HTML or change SQL/schema/fixtures to improve the result.
