"# Спецификация: Soft-delete, корзина и восстановление документов

## Требования

### Требование 1: Реализация мягкого удаления (Soft-delete)
- При удалении документа (`DELETE /api/documents/{id}`) документ НЕ должен физически удаляться из базы данных.
- Система должна устанавливать статус документа в `DELETED`.
- Перед переводом в статус `DELETED` система должна сохранять предыдущий статус документа (`DRAFT` или `PUBLISHED`) в поле `previous_status`.
- Система должна сохранять информацию о предыдущем родителе документа в поле `previous_parent_id`.
- Удаленные документы должны автоматически исчезать из обычного пространства, списков документов, дерева навигации, пагинации и поисковой выдачи.
- Запрещено прямое изменение статуса `DELETED` через стандартные эндпоинты обновления (`PUT /api/documents/{id}`).

### Требование 2: Сохранение и переподчинение иерархии при удалении
- Документы имеют древовидную структуру с родительскими связями (`parent_id`).
- При удалении родительского документа его прямые дочерние элементы должны автоматически переподчиняться родителю удаляемого документа (родителю верхнего уровня / \"дедушке\").
- Информация об исходном непосредственном родителе должна сохраняться в поле `previous_parent_id` каждого дочернего документа.

### Требование 3: Административная корзина
- Система должна предоставлять отдельный специализированный интерфейс и API-эндпоинт (`GET /api/admin/documents/recycle-bin`) для административной корзины.
- Корзина должна отображать исключительно документы со статусом `DELETED`.
- Доступ к административной корзине и операциям в ней должен быть строго ограничен пользователями с системной ролью администратора (`is_admin = true`).

### Требование 4: Восстановление документов и иерархии
- Администратор должен иметь возможность восстановить удаленный документ через специальный эндпоинт (`POST /api/admin/documents/{id}/restore`).
- При восстановлении документа:
  - Статус документа возвращается к предыдущему значению (`DELETED` → `previous_status`, то есть `DRAFT` или `PUBLISHED`).
  - Восстанавливается родительская связь из `previous_parent_id`.
  - Если предыдущий родитель также находится в статусе `DELETED` или удален, система должна автоматически определить ближайшего доступного предка (\"дедушку\").
  - Если пространство документа или вся цепочка родителей удалена/недоступна, операция восстановления должна быть заблокирована с возвратом ошибки.
  - Поля `previous_status` и `previous_parent_id` очищаются (`null`).

## Сценарии (Acceptance Criteria)

### Сценарий 1: Мягкое удаление документа
- **Given**: Документ находится в статусе `PUBLISHED` (или `DRAFT`) и имеет дочерние элементы.
- **When**: Пользователь выполняет удаление документа.
- **Then**: 
  - Запись остается в базе данных со статусом `DELETED`.
  - Предыдущий статус (`PUBLISHED`) сохраняется в `previous_status`.
  - Исходный родитель сохраняется в `previous_parent_id`.
  - Документ исчезает из обычного списка, поиска и дерева навигации.

### Сценарий 2: Переподчинение дочерних элементов при удалении
- **Given**: Иерархия документов: A -> B -> (C, D).
- **When**: Документ B удаляется.
- **Then**: 
  - Статус B становится `DELETED`.
  - Документы C и D меняют свой `parent_id` на A.
  - В полях `previous_parent_id` документов C и D сохраняется ID документа B.

### Сценарий 3: Административная корзина
- **Given**: В системе есть несколько удаленных документов со статусом `DELETED`.
- **When**: Администратор открывает интерфейс корзины (`/admin/recycle-bin`).
- **Then**: 
  - Отображаются только документы со статусом `DELETED`.
  - Обычный пользователь (не администратор) получает отказ в доступе к корзине (`403 Forbidden`).

### Сценарий 4: Восстановление документа и иерархии
- **Given**: Документ B находится в корзине со статусом `DELETED` и `previous_status = PUBLISHED`.
- **When**: Администратор выполняет восстановление документа B.
- **Then**: 
  - Статус B возвращается в `PUBLISHED`.
  - Восстанавливается родительская связь B с исходным родителем.
  - Поля `previous_status` и `previous_parent_id` сбрасываются.
  - Документ снова появляется в обычном пространстве.

### Сценарий 5: Запрет редактирования и прямого изменения удаленных документов
- **Given**: Документ находится в статусе `DELETED`.
- **When**: Пользователь пытается изменить содержимое документа через `PUT /api/documents/{id}` или изменить статус напрямую.
- **Then**: 
  - Система отклоняет запрос с ошибкой (400/403), защищая удаленный документ от некорректных модификаций."
