# Quality gates (перед завершением change)

Цель: минимально гарантировать, что фича корректно встроена в систему и не ломает сборку.

## Обязательный минимум (backend)
Запускать из каталога `backend` в клонированном репозитории. Требуются JDK 17/21 и Maven.

1) Сборка:
- `mvn clean compile`

2) Тесты:
- `mvn test`

Один эквивалентный полный прогон: `mvn clean verify` (компиляция, тесты, упаковка JAR и отчёт JaCoCo).

3) Smoke-check API (опционально, если есть окружение):
- `mvn spring-boot:run` (dev, требуется PostgreSQL)
- затем проверить `/actuator/health`

## Полная проверка репозитория

Из корня репозитория:

```sh
node --test backend/src/test/javascript/*.test.js tests/performance/*.test.cjs
python3 -m unittest discover -s tests/rag -p 'test_*.py'
openspec validate --all --strict
```

На macOS при изменениях `scripts/local/` дополнительно проверяйте безопасное управление локальными процессами и конфигурацией:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/local -p 'test_*.py'
```

Успех этих проверок не заменяет реальный stop/start постоянного стека и проверку сохранности данных; выполняйте их на подготовленном локальном окружении по [инструкции](../docs/LOCAL_SETUP_RU.md).

При изменениях Docker/Compose, контейнерной инициализации или `scripts/dev/`/`run-e2e.sh` дополнительно запускайте из корня репозитория в Linux/macOS:

```sh
docker compose --env-file /dev/null config --quiet
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/docker -p 'test_*.py'
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/dev -p 'test_*.py'
```

Проверки `scripts/docker` используют временные каталоги и локальный mock HTTP: проверяют атомарность и сохранность секретов, отказ при несовместимом состоянии томов, загрузку только отсутствующих моделей, форму embedding/ответа и таймауты. Проверки `scripts/dev` подставляют тестовый Docker CLI и проверяют изоляцию E2E-проекта и его очистки. Ни один из этих наборов не запускает настоящие контейнеры или модели и не заменяет Docker-приёмку.

Для Docker-изменений отдельно проверьте настоящий чистый старт без `.env`, готовность зависимостей и моделей, UID/порты/тома, повторный старт и сохранность данных/секретов после обычного `down`/`up` по [Docker-инструкции](../docs/DOCKER_LOCAL_RU.md). Браузерные проверки запускайте через `./run-e2e.sh` в отдельном Compose-проекте; реальный RAG проверяйте отдельно от его тестового пропуска загрузки моделей. Сохраняйте фактические результаты и не отмечайте эти действия выполненными по результатам mock-тестов.

Браузерные тесты требуют запущенного приложения с PostgreSQL и тестовым администратором `admin/admin123`. Используйте отдельную тестовую БД, Git-репозиторий и blob-каталог; выключите внешние AI и уведомления. Тесты создают и изменяют данные.

```sh
cd tests/E2E
npm ci
npx playwright install chromium
E2E_BASE_URL=http://127.0.0.1:18080 npm test
```

В конфигурации Playwright: один worker, retries=0. Перед полным прогоном используйте свежую тестовую схему и JAR из текущей сборки. Не очищайте рабочую или общую БД. Обычные тестовые API-клиенты получают серверную CSRF-cookie и передают заголовок; отрицательные проверки CSRF используют отдельный raw client.

Для каждого исправления сохраняйте результаты в OpenSpec tasks и `tests/E2E/E2E_RESULTS.md`. Нагрузочная приёмка US4.4.1 описана в `tests/performance/README.md`: согласованный нормальный профиль — 25 пользователей, отдельный стресс — 50. Она дополняет функциональные тесты; её измерения запускаются без параллельных сборок, E2E и модельного inference. Неуспешные замеры и исходные пороги сохраняются вместе с итоговым результатом.

При изменении RAG retrieval или промпта дополнительно запускайте реальные локальные модели по `tests/rag/README.md`: исходные 30 вопросов и расширенный набор с обязательными источниками из нескольких статей. Сохраняйте исходные ответы и параметры; успешные mock-тесты не заменяют проверку качества модели.

## Если нет PostgreSQL
Не менять security/авторизацию “для демо” в main-ветке.  
Для проверки без Postgres используйте тесты (`mvn test`), или поднимайте Postgres локально по `backend/readme.md`.
